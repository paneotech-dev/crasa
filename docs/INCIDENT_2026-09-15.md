# Security incident, 15 September 2026

**Platform:** CRASA Digital Anchor Ecosystem, development host
**Domains affected:** `crasadev.paneo.tech`, `crasa.paneo.tech`
**Hosting account:** `ptechweb` (a shared cPanel account holding about 29 sites)
**Detected:** 15 September 2026, about 12:03, during a pre-workshop readiness check
**Contained:** 15 September 2026, 12:38, both CRASA domains taken offline
**Status:** contained for CRASA; the account is to be reimaged by the host
**All times:** server time, UTC+2

---

## Summary

The hosting account that runs the CRASA development platform was
compromised by an automated attack toolkit, most likely one of the
AnonymousFox family that targets cPanel accounts. The attacker could run
code on the server from 2 September onward and used that access on
15 September to install web shells in the CRASA site.

**We found no evidence that the application code in git was tampered
with.** How that was checked, and the limits of the check, are set out
below.

The CRASA database held very little personal data: seven user accounts,
six of them test accounts. No delegate registrations, contact-form
enquiries or directory contacts had been stored.

The attacker did not sign in to the CRASA application. They did not need
to: they had the server itself, and with it every secret the application
holds. All of those secrets are being replaced, and the platform is being
rebuilt on a clean host from git.

## How the attacker kept access

**A crontab that rebuilds the dropper.** The account's crontab had 36 lines
added, one per website folder. Each runs every minute and rewrites a small
file-writing script, always the same script (SHA-256 beginning
`6b28d03d87aeece7`), if it has been deleted. One of the 36 targets the CRASA
site. Deleting the attacker's files without first clearing the crontab
brings them back within a minute.

**Loaders owned by root.** The loaders are owned by `root` and are
world-writable. A process running as the `ptechweb` user cannot create a
file owned by `root`. The access therefore reached above the level of the
account, and only the hosting provider can establish how.

**Mailboxes on every domain.** Creating mailboxes on each domain is how
this family of toolkits takes over a cPanel account: a password reset sent
to a mailbox the attacker controls.

**PHP protections switched off.** The injected `php.ini` files allow PHP to
run operating-system commands, which is what the shells need.

## What was exposed

Anything the `ptechweb` user can read, because the shells run as that user.

| Item | Why it matters |
|---|---|
| The CRASA `.env` file | Database password, application key and mail settings. The file was world-readable (mode 644). No live mail credentials were in use: mail was set to write to the log |
| The application key | Signs sessions and encrypts sensitive fields. Administrators' two-factor secrets are encrypted with it and stored in the database the attacker could also read, so **two-factor protection on those accounts must be treated as broken** until the key is replaced and the accounts re-enrol |
| The database | Seven user accounts with hashed passwords; one administrator's encrypted two-factor secret and recovery codes; one real email address; the imported CRASA content, which is public |
| A text file of test-account passwords | The six test accounts' passwords, in plain text, in the account's home folder |
| The account's git credentials | A token in `~/.git-credentials`, now being revoked |
| The account's SSH private keys | Any server those keys can reach should be treated as exposed |
| The scraped archive of crasa.org | Public content, so nothing confidential; but it could have been altered, so it is re-checked against the live site before reuse |

## What was not exposed, or not present

- **No delegate registrations, enquiries, directory contacts or feature-interest records.** Each table had zero rows.
- **No sign-in to the CRASA application by the attacker.** The audit log has no entry from any of the three attacker addresses. Every sign-in since 2 September came from addresses the development team recognises, pending one confirmation by the account owner.
- **No live SMTP credentials.** Mail was not yet connected.
- **No production CRASA site.** The platform had not gone live.

`crasa.paneo.tech` is a separate, earlier CRASA application on the same
account. It is not built from this repository and this report does not
assess what it held. It was compromised in the same way, three of the
attacker's mailboxes were created on its domain, and it was taken offline
at the same time as the development site.

## Was the application code tampered with?

**We found no evidence that it was.** Five checks, all run on 15 September:

1. **Injected code.** Every PHP file in `app`, `bootstrap`, `config`, `database`, `routes`, `resources`, `vendor` and `public/index.php` was searched for the patterns web shells use: `eval` of compressed or encoded strings, `assert` on request input, calls built from request variables, `preg_replace` with the execute flag. **No matches.**
2. **The work not yet committed.** All 119 changed files were searched for those patterns and for `shell_exec`, `passthru`, `proc_open`, `system(`, `exec(`, `fsockopen`, `move_uploaded_file`, long hex runs and long base64 blobs. **No matches.** None of those files was modified after 10 September 16:35, five days before the attack on the CRASA site.
3. **Git's own integrity.** `git fsck --full` reports the object store consistent. The repository has no hooks and its configuration has no hook path, filter, pager or URL rewrite that could run code.
4. **History.** The reflog shows 125 ordinary commits, one amend and two no-op resets: no rebase and no rewrite. 89 of the 126 commit identifiers were printed in the development session records at the moment each commit was made, and all 89 still name the same change.
5. **The entry point.** `public/index.php` is unchanged since the first commit. No `.user.ini`, `php.ini` or `.htaccess` anywhere on the account injects code into PHP requests through `auto_prepend_file`.

**The limits of those checks.** The repository has never been pushed to a
remote, so there is no copy held anywhere else to compare it with, and
every commit was made after the attacker had access. A careful attacker
who edited a source file in a way that matches none of the patterns above
would not be caught by them. For that reason the rebuild includes a human
review of the uncommitted work before it is trusted, and the platform's
1,580 automated tests are run on the clean host.

## Containment, in order

The order matters. Each step undoes a way back in, and doing them out of
order lets the attacker restore what was removed.

| # | Action | Owner | Status |
|---|---|---|---|
| 1 | Take both CRASA domains offline | Development team | Done, 12:38 |
| 2 | Rescue the uncommitted work and the scraped archive into a folder outside every docroot, by explicit file list, with checksums | Development team | Done |
| 3 | Copy that folder off the server and check every checksum on the receiving machine | Account owner | Pending |
| 4 | Report to the hosting provider and ask them to preserve a forensic image before anything is removed | Account owner | Pending |
| 5 | Change the cPanel password and contact email; delete every `info-` mailbox and any FTP account nobody recognises | Account owner | Pending |
| 6 | Clear the 36 crontab entries | Hosting provider | Pending |
| 7 | Revoke and replace: the git token, every SSH key, the database password, the application key, mail credentials; delete the test-account password file | Account owner and development team | In progress |
| 8 | Reimage the server | Hosting provider | Pending |
| 9 | Rebuild the platform on the clean host | Development team | See `docs/REBUILD.md` |

Nothing was deleted or cleaned on the compromised server. Its files, access
logs and database are evidence and go with the reimage unless the host
preserves them first.

## The rebuild

The platform is stood up again from git and from the scraped archive, not
from anything else on the old server. The full procedure is in
`docs/REBUILD.md`. In outline:

1. Restore the repository from the rescue bundle and verify its checksum.
2. Review the uncommitted work that the rescue commit captured.
3. Install on a clean host with fresh credentials for everything.
4. Re-import CRASA's content directly from crasa.org and the events site,
   using the import commands already in git. The old database is not
   restored.
5. Re-verify a sample of the scraped archive against the live site before
   using it.
6. Recreate accounts. Administrators enrol in two-factor authentication
   again at first sign-in.
7. Run the full test suite, the security checks and the content audit
   before the domains go back online.

---

## What changes as a result

- **Secrets are never world-readable.** `.env` is mode 600 on the new host.
- **Passwords are never written to a file on a server.** Test-account
  passwords go straight into a password manager.
- **The repository is pushed to a private remote from the first day,**
  so there is always a copy off the server to compare against.
- **Backups exist before content does.** `docs/BACKUP_SETUP.md` is carried
  out on the new host before the import runs.
- **The platform does not share a hosting account with unrelated sites.**
  This compromise reached CRASA through a shared account, not through the
  application.
